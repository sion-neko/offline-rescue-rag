# 0013 原本は QA の形で持ち、QA の質問と比べて検索する

- 状態：採用（閾値は仮）
- 日付：2026-11-18

## 背景
- 見出しごとのマニュアル（0011）を、見出しごとの「題名＋本文」のベクトルで検索していた。条件が重なる質問や、資料にない質問で次の問題が出た
  - 条件が重なる質問（「雨で濡れて寒いし、電波も入らない」）で、片方の条件の資料が候補に入らない
  - 上位 3 件を数合わせで AI に渡すので、逆の行動の資料が混ざる（「暑くて足がつった」に低体温症）
  - 資料にない質問（「ハチに刺された」）と、答えられる質問の点数が近い
- よくある質問は答えを用意しておき、想定外の質問だけ LLM に回す方針にした（本人：「条件が重なる質問に QA をいくつも返されても理解が難しい」ので LLM は残す）

## 決定
- 原本は `data/qa/*.md` に QA の形で書く。`## 質問`、`分類:`、`言い換え:`、`関連:`、答えの行（やる順、0012 の順番）。同じ行が複数の QA に入ってもよい
- 検索は、質問を QA の**質問・言い換え**と比べ、いちばん近いものの点数を使う（`similarityPrefix` どうし）
- 1 位の点数が `minScore` 未満なら「資料に見つかりませんでした」。1 位から `usedMaxGap` 以上離れた QA は使わない（数合わせを防ぐ）
- 2 位以下の QA は、条件が重なる質問のもう片方の条件として「あわせて確認」に出す
- 見出しごとのマニュアル（`data/manual/`）は消した。移したとき、マニュアルの 48 行がすべてどれかの QA に入っていることを確かめた

## 検討した案（24 問で比較、`docs/retrieval-comparison.md`）
- 見出しごとのベクトル（今までの形）：1 位は全問正しいが、条件が重なる質問で 1 問、片方の条件が上位 3 件に入らない
- 行ごとに点数を付ける（small-to-big）：どの資料にも「なんとなく似た行」があり、点数が詰まる。条件が重なる質問で 2/8
- LFM3 に「はい／いいえ」で判断させる（Decision RAG の考え方）：ほとんどの質問で「通報のしかた」に「はい」を付け、1 位が正しいのは 1/16。1 回 0.84 秒（PC の CPU）
- **QA の質問と比べる**：1 位は全問正しく、条件が重なる質問 8/8。QA が「1 つの状況」の単位なので、条件ごとに分けなくても条件ごとの QA が並ぶ

## 結果
- 言い換えの辞書（`data/synonyms.json`）はアプリでは使わなくなった。言い換えは原本に書く（0009 を置き換え）
- 「あわせて確認」は「関連」ではなく 2 位以下の QA から出す（0008 の一部を変更）
- `minScore` 0.75・`weakScore` 0.82・`usedMaxGap` 0.1 は仮の値。資料にない質問で、まだ「関係が薄いかも」付きで答えが出るもの（蛇にかまれた → けが人）がある
- QA の言い換えもテストの質問も Claude が書いたので、測った結果は QA に有利なおそれがある。本人のテストで測り直す
